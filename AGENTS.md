# Swtcon Re-Implementation Plan & Status

Our goal is to sever the dependency on the black-box `libqsgepaper.so` library by fully reversing and re-implementing the Software Timing Controller (swtcon) logic natively in C++.

**The goal is full independence — no exceptions by default.** Every function
still called into the library by address (`resolve_ptr<...(*)...>(0x...)`) is
a dependency that needs to eventually go. Sizing something "large" just means
"port last, after everything smaller" — never "skip." As long as any
function is still called by address, the whole library stays `dlopen`'d and
mapped, so nothing is actually exempt.

**Update:** as of this pass, there are zero remaining by-address *function*
calls anywhere in the production pipeline (see Phase 5/6 and the playback-
kernel entry below) — the last one, `FUN_0004a234`, is gone. **Update 2:**
Phase 7 is also now done — every `resolve_ptr<T*>(addr)` *data* access into
the library's `.bss`/`.data` (the update-queue state, framebuffer/statebuffer
globals, mutexes, the dirty-gate array, a vtable pointer) has been replaced
with natively-owned storage (see the Phase 7 entry below). The only thing
left standing between this codebase and never `dlopen`-ing
`libqsgepaper.so` at all is Phase 8 (gating `load_lib()` itself behind
`SWTCON_LIBDISPATCH`, off by default) — a small, already-scoped step now that
Phase 7 has removed the actual data dependency.

See `swtcon_architecture.md` for a standing reference on *how the system
works* (data formats, control flow, algorithms, native and still-library
parts together, with confidence tags on anything not byte-verified). This
file tracks phase-by-phase porting *status* instead — what's done, what's
left, and what to do next.

- **`dispatch_processed_regions` — SOLVED, native, and WIRED IN (confirmed on the emulator).** What looked like a genuine cross-item rectangle-merge algorithm (an earlier framing) turned out, on empirical investigation via a dedicated tool (`tools/qsgepaper-preload/dispatch_processed_regions_probe.cpp` — calls the real library function directly with controlled synthetic `WorkItem` batches and reads back what actually happened, same technique as `render_kernel_addr_map.cpp`), to be **per-item-only bookkeeping with zero cross-item interaction** — 7 passing experiments including the definitive one (two independent items in one batch, dispatched together; the unrelated item's rect came back completely unaffected). Also nailed down `FUN_0004f8f0`/`FUN_0004e680`'s exact per-pixel packing formula: the packed transition value is `(oldState<<5)|newValue` and the "unchanged" sentinel is `0x0400`. See `swtcon_architecture.md` §6.2 step 4 / §6.3. The native port (`native_dispatch_processed_regions_native`/`native_commit_item` in `native_display.cpp`) is wired in at the real call site. **The "integration hazard" that previously kept it by-address — a deterministic SIGSEGV in the still-library `FUN_0004a234` on the first HQ update — was a stale `WorkItem.stateDataPtr` (+0x44), not `FUN_0004a234` itself.** The real `dispatch_processed_regions` caches `sp3.ptr->dataPtr` into `item+0x44` right after allocating `sp3`, and both playback kernels (`FUN_0004a140`/`FUN_0004a234`) read their per-pixel state through that cached pointer, not via `sp3.ptr->dataPtr`; `native_commit_item` now sets it. That's exactly why the earlier elimination log (not downstream state, not `sp3` content, not timing, not global init) came back all-negative — none of those touched +0x44. **Confirmed on the emulator** with the native path live: clean `EXIT=0` across HQ/medium/clearing plus all five overlap tests, continuous `FBIOPAN`, clean shutdown. **Confirmed on hardware too**, after one follow-up fix: +0x44 is not the sp3 buffer *base* — it's that base **rebased to the item's post-narrowing rect origin** (`sp3.dataPtr + stride*(rectX0-sp3.x0) + (rectY0-sp3.y0)`, the same rebasing as `gap` vs `regionRows`). The incremental commit narrows `item.rect` inward from the 8-aligned seed the sp3 buffer was sized for, and the playback kernels index +0x44 with narrowed-rect-relative coords. Seeding it to the base (offset 0) is correct only for the force path and unsplit items; for any narrowed/split item it read state one column + 8 rows off → **edge artifacts** (white seams where an update overdrew a previous one), visible only on real e-ink since the digital state/framebuffer settle identically. Found via a native-vs-library A/B harness (`SWTCON_LIBDISPATCH` env toggle, still in `native_display_thread_func`) that diffs the *transient* waveform frames — the library's +0x44 came back as `sp3.dataPtr + 0x670` on a narrowed item, exactly `stride*(804-803)+(1072-1064)`. `native_commit_item` now rebases it after narrowing.

- **`FUN_0004a140` ("plain" playback kernel) — SOLVED, native, and WIRED IN (confirmed on the emulator).** Reversed via `tools/qsgepaper-preload/playback_kernel_probe.cpp`, the same "dlopen the real library, call the real function directly with a controlled synthetic `WorkItem`, read back what happened" technique as `render_kernel_addr_map.cpp`/`dispatch_processed_regions_probe.cpp`. Every buffer the probe hands the kernel (state buffer, LUT data, the `frameSlots[8]` pointer array itself, even the `WorkItem`'s own containing node) is backed by an `mmap` `PROT_NONE` guard page on both sides — a first pass with plain `malloc`'d buffers found the kernel call "returns without crashing" but silently corrupts memory, discovered only much later at an unrelated `free()`; guard pages turn that into an immediate, localizing `SIGSEGV`. (The actual first corruption culprit turned out to be a bug in the probe itself, not the kernel: `LUTEntry`'s destructor unconditionally `free()`s `.data`, and `TestItem` embedded a `LUTEntry` by value, so it fired on every guard-paged LUT buffer at scope exit — nulling `.data` before that fixed it. Worth remembering next time a "clean return, corruption discovered later" pattern shows up: check for an implicit destructor on a raw pointer field before suspecting the library call.) When black-box probing alone stalled (zero output from a plausible-looking call), reading `FUN_0004a140`'s Ghidra decompile directly (via the `mcp__ghidra__decompile_function` MCP tool, `libqsgepaper_3.23.0.54.so`) resolved it immediately rather than more guessing. Fully confirmed and ported (`native_playback_kernel_plain` in `native_display.cpp`):
  - The LUT-index formula matches the already-native `native_read_lut_packed_pixel` exactly: the raw `stateDataPtr` (+0x44) u16 per pixel is used directly as `mw*row+col` (a flat multiply-add, *not* a `>>5`/`&0x1f` split — only numerically identical to the `(oldState<<5)|newState` packing confirmed elsewhere in this codebase because `mode_width==32` in that case).
  - The destination address formula: `frameSlots[k] + ((col + 3)*0x104 + (rectY0>>3) + group + 0x1a) * 4` (`col` absolute, `group` the 0-based 8-row-group index within the rect, `k` the output-frame index) — byte-verified against five targeted probe experiments (single group, multi-group at `base+group*4`, and multi-column chunking).
  - Y is block-quantized by 8 (`((rectY1-rectY0)+1)>>3` gates the whole write loop — a literal 1×1 test rect silently no-ops here, which is why the probe's first few runs produced zero output with no error); X is not block-quantized.
  - Drive values are 2-bit; within one 8-row group, row `r` (0-based from the group's start) OR-accumulates into bit position `(7-r)*2` of a 16-bit word — row 0 at the *top*, row 7 at the *bottom* (confirmed via 8 isolated single-row probe experiments), matching this codebase's established 180°-rotation convention rather than a naive lane order.
  - `frameCount` (1–8) does **not** mean N independent LUT lookups: the kernel computes an 8-entry shared buffer once per column/row-group (one entry per possible sub-phase 0–7 packed into the current LUT word) and `frameSlots[k]` just reads out shared-buffer entry `(phase&7)+k` — confirmed both by decompiling case 2 and by a probe experiment planting two different values at adjacent sub-phases of the same LUT word and observing them land in `frameSlots[0]`/`frameSlots[1]` respectively. This is exactly why `native_advance_work_item_frames` always picks `frameCount` so `phase&7+frameCount` never crosses an 8-sub-phase LUT-word boundary — the native port needs no case-by-case logic at all, just one parametrized loop.
  - `FUN_0004a140`'s prologue jump-tables on `frameCount` 0–8; case 0 falls through to a *second*, Ghidra-unrecoverable nested jump table (`Could not recover jumptable at 0x47be8`) — irrelevant here since `native_advance_work_item_frames` never calls the plain-kernel path with `frameCount==0` (guarded by its own early-return).
  - The function calls no allocation/free, touches no global (`DAT_*`) addresses, spawns no threads, and never writes to `*item` — every `item` field it touches (`0xc`/`0x10`/`0x14`/`0x18`/`0x28`/`0x2c`/`0x3c`/`0x44`) is read-only, and mode_width/bit_depth aside, the 2-bit/8-row packing constants are hardcoded immediates in the real kernel too (matches `native_load_waveform` always producing `bit_depth=2` LUTs).
  - **Confirmed on the emulator** via the full `swtcon-ab-test` A/B pipeline (not just the isolated probe): `KERN` log coverage shows the real test matrix exercises the plain kernel exclusively at `frameCount=8`; a native-vs-library `--compare` run matched byte-for-byte everywhere except `seq=26-29`, which is the pre-existing documented real-time-jitter window (case 8/9's `usleep`-based submissions) — confirmed noise, not a regression, since a native-vs-native rerun shows the identical mismatch pattern with the library entirely out of the loop.
- **`FUN_0004a234` (playback kernel; formerly called "overlap-aware" here - corrected to "aligned", see below) — SOLVED, native, and WIRED IN (confirmed on the emulator).** Turned out **not to be a distinct algorithm at all.** Rather than reversing it independently, a decisive test (`playback_kernel_probe.cpp` Experiment 7) calls both `FUN_0004a140` and the real `FUN_0004a234` on an *identical* synthetic `WorkItem`/state/LUT (a rich, pseudo-random, non-uniform fill spanning 4 columns × 16 rows, so a coincidental match is implausible) for every `frameCount` 1–8 — **including the three cases (1, 2, 3) that `FUN_0004a234` itself tail-calls out to separate, still fully unreversed delegates** (`FUN_0004a3f8`/`FUN_0004a9e0`/`FUN_0004b098`) **for** — and diffs every byte of the output: all eight cases came back byte-for-byte identical. A Ghidra decompile of case 8 (94/117 real overlap-kernel calls in one `ab-test` run, vs. 23 for case 5 and 0 for every other case — checked via the `KERN` log before investing in a decompile) independently corroborates this: it touches the *exact same* `WorkItem` fields as `FUN_0004a140` (`0xc`/`0x10`/`0x14`/`0x18`/`0x28`/`0x2c`/`0x3c`/`0x44`), the same LUT-index formula, the same destination address formula, and the same row→bit packing order — no new field, no global, no `intList` access, no allocation, no threads. The only difference is NEON unrolling strategy: cases 4–8 extract all 8 sub-phases from one lane-shifted vector at once (valid only because the selection rule guarantees `phase&7==0` whenever this path is taken, so there's no `(phase&7)+k` offset to compute, unlike `FUN_0004a140`'s general case). **Naming correction (this pass): `FUN_0004a234` and its dispatch wrapper were previously called "overlap-aware"/`native_dispatch_overlap_kernel` — backwards, since (per `advance_work_item_frames`'s selection rule, `swtcon_architecture.md` §6.4) this path fires exactly when there is *no* active overlap dependency left, gated only on `phase&7==0`. Renamed to "aligned"/`native_dispatch_aligned_kernel` throughout the code, the `KERN` A/B-capture log tag, and this doc.** **Net result: `native_playback_kernel_plain` now backs *both* `native_dispatch_plain_kernel` and `native_dispatch_aligned_kernel`** (`native_display.cpp`) — one native function, zero remaining by-address playback-kernel calls, and the three delegates never need reversing at all. **Confirmed on the emulator**: the full `swtcon-ab-test` A/B pipeline's `STATE` records (the settled, final pixel-level output per test step) match the library **perfectly, zero mismatches, across all 9 test cases** — the only remaining `--compare` divergences are transient `PLAY` per-frame-capture timing jitter (inherently real-time-dependent, the same documented class of noise as `seq=26-29`'s case 8/9 window, now also touching `seq=10` purely because native code runs at different wall-clock speed than the by-address call did, shifting which real-time frame tick a capture lands on — confirmed non-causal by reproducing the identical `seq=10` mismatch in a native-vs-native rerun with the library entirely out of the loop) and the pre-existing, already-documented `seq=28/29` `DISP` noise. `qsgepaper-test`'s full interactive suite (including the two playback-coverage scenarios) also runs clean, `EXIT=0`, on the emulator.
  - **Follow-up ("there must be a reason they're separate functions"):** decompiling `FUN_0004a3f8` (case 1's delegate) directly answers this — the code really is meaningfully different, not a trivial duplicate. It does alignment-based column-chunking (`-(((uint)ptr & 0x3f) >> 4) & 3`-style leading/trailing-remainder splitting) and an 8×4 transpose/prefetch bulk loop, structurally unlike `FUN_0004a140`'s simple one-column-at-a-time loop — genuine hand-tuned NEON engineering, most likely per-`(frameCount, phase-alignment)` performance specialization (`FUN_0004a140` is the fully general case, needing the `(phase&7)+k` slice for arbitrary alignment; `FUN_0004a234`'s cases 4-8 and the three delegates are all fast paths only valid at `phase&7==0`, some further specialized for wide-column bulk throughput). Critically, it still touches only the *exact same* `WorkItem` fields as everything else here — no `intList`, no new global, no allocation — so "why a separate function" has an engineering answer (performance), not a semantic one (no code path here has any way to observe or react to *another* item's overlap-dependency state; that's entirely the caller's `advance_work_item_frames` selection-rule's job, see `swtcon_architecture.md` §6.4). Re-ran the identical-input diff specifically designed to stress the parts that differ - a 128-column rect (wide enough to exercise the bulk transpose path, not just the tail/remainder handling a narrow rect would trivially hit either way) and explicit `chunkCount=2` splitting (exercising `FUN_0004a3f8`'s own independently-computed chunk boundary, not just `FUN_0004a140`/`FUN_0004a234`'s shared one) - still byte-for-byte identical across every case. Xrefs confirm neither kernel is called from anywhere but its own wrapper (`FUN_0003f294`/`FUN_0003f1f0`), so there's no other call site hinting at a different intended use either.

- **Phase 7 — Global storage independence: COMPLETE (confirmed on the emulator).** Every remaining `resolve_ptr<T*>(addr)` *data* access into the library's `.bss` is gone - the four structs (`UpdateQueueGlobals`, `FrameCursorGlobals`, `StatebufferGlobals`, `FramebufferGlobals`), the four standalone scalars (pid fd, cached temperature, temperature mutex, seq counter), the backBuffer dirty-gate array, and the RegionRows shared_ptr vtable are all natively-owned storage now (`qsgepaper_globals.h`'s accessors are function-local `static` instances instead of `resolve_ptr<T*>(fixed_addr)`; `native_update.cpp`'s `kNativeRegionRowsVtable` mirrors the `dispose`=array-delete/`destroy`=delete convention `native_make_empty_lut`'s `kNativeLutVtable` and `native_display.cpp`'s `kNativeSp3Vtable` already used). The three previously-implicit pieces got added, not just relocated: the three `ListHead` sentinels (`listProcessedUpdates`/`listIncomingUpdates`/`accumList`) are now explicitly self-referenced at the top of `swtcon_init`; the waveform vector (`g_nativeWaveformStruct` in `swtcon.cpp`, no longer "deliberately leaked") is walked and freed in `swtcon_shutdown`; the temperature mutex gets an explicit `pthread_mutex_init` alongside the others. As a genuine drive-by fix (not scope creep - it's the same pid-fd global this phase was already touching): `native_unlock_pid_file` was reading the *library's* still-zero pid-fd slot instead of `native_create_pid_file`'s own `g_nPidFdNative`, a latent dead-code bug now corrected.
  - **Two real bugs surfaced during validation, both worth remembering.** First, `native_stale_row_cleanup`'s documented "backward `i%16` reach" quirk (§ next steps below) used to land safely in the library's own huge `.bss` region; a bare native array has no such margin, so the first swtcon-ab-test run after the refactor **segfaulted immediately at startup**. Fixed by padding `backbuffer_dirty_gate()` with `kDirtyGateBucketCount` extra always-zero buckets before the real array and returning a pointer into the middle - same observable behavior (the padding is provably never legitimately written), just safe to reach. Second, and much more interesting: fixing the first bug uncovered a **pre-existing, silent heap-buffer-overflow read in `native_playback_kernel_plain`** (`native_display.cpp`, dates to Phase 5) that had nothing to do with Phase 7's own diff - it read `state[sp3->stride*(col-sp3->x0)+(row-sp3->y0)]`, double-applying the sp3-rebase offset on top of a `stateDataPtr` that's *already* rebased to the item's own rect origin (see `native_commit_item`'s +0x44 comment), overrunning the sp3 buffer for any narrowed item by up to a few hundred bytes. It had been silently reading adjacent-but-mapped heap memory for every phase up through Phase 6 without ever crashing or showing up in an A/B mismatch; Phase 7's different static/heap layout was enough to occasionally push the same over-read into an unmapped page, turning silent corruption into a hard, semi-reproducible `SIGSEGV`. Root-caused in minutes rather than hours via a throwaway AddressSanitizer build (`cmake --preset dev -B build/asan -DCMAKE_CXX_FLAGS="-fsanitize=address -g -O0 -fno-omit-frame-pointer" -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address"`, then `LD_PRELOAD=./libasan.so.8:./libioctl-dump.so` with `libasan.so.8.0.0` copied over from the toolchain sysroot) - it caught the exact faulting read, the exact allocation site, and the exact overrun distance on the very first narrowed item, no manual bisection needed. Worth remembering for next time a native port "works" on every A/B run but only because the overrun is silently landing on other live heap data: **when a bug is timing/layout-sensitive and a plain SIGSEGV handler's backtrace is too shallow to trust (ARM's `backtrace()` frequently can't unwind through a signal frame - a `SA_SIGINFO` handler reading `ucontext_t.uc_mcontext.arm_pc` directly is more reliable), reach for ASan before hand-bisecting.** Fixed by indexing `state[]` relative to the item's own rect origin (`stride*(col-item->rectX0)+(row-item->rectY0)`) instead of sp3's - algebraically the same absolute buffer element, but without the double offset; the item's rect is always a subset of sp3's outward-8-aligned rect, so this is provably always in-bounds. Confirmed clean under the ASan build afterward (aside from one unrelated, harmless, pre-existing `malloc`/`operator delete` mismatch in `native_free_statebuffer`'s gamma-table free, suppressed via `alloc_dealloc_mismatch=0` - glibc's `free()` and libstdc++'s default `operator delete` are the same function under the hood, so this is a strictness-only ASan complaint, not a real bug).
  - **Validation caveat:** the existing `SWTCON_LIBDISPATCH=1` A/B path (real library's `dispatch_processed_regions` called by address) is now **structurally non-functional**, not a new regression to chase - it depends on the native side and the library sharing the same backing globals, which is exactly what this phase removes. Calling it now reliably `SIGSEGV`s on the real function reading its own (now permanently stale) `.bss`. Validated instead the way this codebase already validates native determinism: two independent post-fix `swtcon-ab-test` runs captured byte-for-byte identical (`--compare` exit 0, 3994/3994 records), plus a full `qsgepaper-test` interactive run (`EXIT=0`). Byte-diffing against a pre-Phase-7 capture turned out not to be meaningful either - real-time backlog ("generator thread has fallen behind...") volume varies a lot run-to-run regardless of phase, so record *counts* differ; determinism (this run vs. itself) is the correct invariant here, not sameness against an unrelated run's capture.

5. **Phase 9 (NEON-optimize the playback kernel) — IN PROGRESS, first vectorization pass done and confirmed on the emulator (real-hardware re-confirmation still pending).** Motivated by real hardware confirmation (`real-dev-bench.txt`, captured before this pass) that `native_playback_kernel_plain` is slow enough to matter: native was 3.3-10.4x slower than the library's plain kernel and 5.2-10.4x slower than its aligned kernel, worst at full-screen. `tools/qsgepaper-preload/playback_kernel_bench.cpp` benchmarks it in isolation (bypassing all threading/dispatch) against the real library's `FUN_0004a140`/`FUN_0004a234` on identical synthetic input, across rect sizes from a single 8-row strip up to a full-panel refresh - see that file for the harness and `swtcon_architecture.md`/AGENTS.md for the scalar port's own derivation.
   - **Split into its own translation unit:** `native_playback_kernel_plain` moved out of `native_display.cpp` into `tools/qsgepaper-preload/native_playback_kernel.cpp` (declaration in `native_display.h` unchanged), so a NEON fast path can live behind an `#ifdef` without dragging in `native_display.cpp`'s threading/globals/`ab_capture` dependencies. Added to every target that previously listed `native_display.cpp` (`qsgepaper-test`, `swtcon-ab-test`, `playback-kernel-bench`) in `CMakeLists.txt`.
   - **NEON path** (gated on `#if defined(__ARM_NEON) || defined(__ARM_NEON__)`, with a portable scalar `#else` fallback for non-ARM builds): vectorizes the per-group inner computation - the 8-row x 8-subphase 2-bit "transpose" that turns each row's packed LUT word into 8 subphase output words. All 8 rows' LUT words are loaded into one `uint16x8_t`, then for each of the 8 output subphases, that subphase's 2-bit field is extracted from all 8 lanes at once (`vshlq_u16` with a per-lane variable shift, then mask), placed at its destination bit position (another per-lane `vshlq_u16` using the fixed `{14,12,10,8,6,4,2,0}` row-order mapping), and the 8 lanes are OR-reduced (`vorr_u16`/`vext_u16` fold) down to the scalar subphase word - mirroring the real library's own strategy here (per the `FUN_0004a234` cases 4-8 analysis above: "extract all 8 sub-phases from one lane-shifted vector at once"), though this is a from-scratch intrinsics implementation of that same vectorization idea rather than a literal transliteration of the library's compiler-generated NEON (`FUN_0004a140`'s body itself was never independently decompiled beyond shape-confirmation - see `swtcon_architecture.md` §8 - only its already-verified formulas were reused). Correct by construction (OR is commutative/associative, so reordering row-outer/subphase-inner to subphase-outer/row-vectorized changes nothing observable) and confirmed empirically: cross-compiling with `-mfpu=neon` (the toolchain's default) emits real `vshl.u16`/`vand`/`vorr`/`vext.8`/`vld1.16` instructions in the object; compiling the same file for the same target with NEON disabled (`-mfpu=vfpv4`) falls back to the scalar loop cleanly, no NEON instructions present, confirming the `#ifdef` actually gates rather than being dead code either way.
   - **Confirmed on the emulator** (RemEmu, `--preset release`/MinSizeRel): `swtcon-ab-test` two independent native runs match byte-for-byte (3994/3994 records, `--compare` exit 0 - the determinism check, since the `SWTCON_LIBDISPATCH` comparison path is still structurally defunct post-Phase-7, see above); full `qsgepaper-test` interactive run clean across HQ/medium/clearing plus the overlap suite, continuous `FBIOPAN` traffic, clean shutdown. `playback-kernel-bench` shows the expected qualitative shift from the pre-NEON baseline ("native holds flat at ~4 Mpix/s regardless of size, scalar, no vectorization"): native now *scales with size* like the library does (4.9→18.0 Mpix/s across the same rect-size matrix), and even beats the library's own plain kernel outright on the two smallest scenarios (0.77x-0.83x its time). Still 2.1x-4.1x slower than lib-plain and 3.3x-13.4x slower than lib-aligned at larger sizes - the per-row LUT-word gather (state read + LUT index, inherently scalar - NEON has no gather on this target) is now the dominant remaining cost, not the bit-transpose this pass vectorized.
   - **Caveat:** all numbers above are emulator-only: RemEmu's NEON is software-emulated (QEMU), so absolute throughput isn't comparable to `real-dev-bench.txt`'s real-hardware numbers - only the qualitative native-vs-library ratio *shape* (flat → scaling) is a meaningful signal, and even that should be re-confirmed on real hardware before declaring this pass done. Next: re-run `playback_kernel_bench` on real hardware (same technique as `real-dev-bench.txt`) to get a trustworthy native-vs-library ratio for this pass, then decide whether the remaining gap (dominated by the scalar per-row gather) is worth a further pass - e.g. prefetching or restructuring the state/LUT access pattern - or whether the transpose vectorization alone is enough to stay inside the panel frame-tick budget for realistic update sizes.
   - **Real-hardware re-run of the NEON pass (`real-dev-bench.txt`, updated):** the NEON transpose alone closed the gap substantially even on real silicon - native is now 0.81x-3.42x the library plain kernel's time (was 3.3x-10.4x pre-NEON) and 2.43x-6.58x the aligned kernel's (was 5.2x-10.4x pre-NEON), i.e. genuinely close to (and at the smallest size, faster than) `lib-plain`. But `slow_commits.txt` (a per-commit log of one real full-screen HQ `swtcon_update()` call's wall-clock duration, via `qsgepaper-test`'s `TIME()`/`Duration:` output) shows the full pipeline is still far from the pre-native-playback-kernel baseline: 100ms → 200ms → 250ms → **850ms** (at `8c00f2e`, the commit that made the "aligned" dispatch path route through the native kernel instead of the library's fast by-address `FUN_0004a234` - the single biggest regression by far) → 780ms with the first NEON pass (this pass only recovered ~70ms of the ~600ms regression). The isolated per-call kernel speedup (real-dev-bench.txt) is much larger in ratio terms than this ~8% pipeline-level improvement suggests, because the pipeline is bounded by absolute compute time against the ~11.76ms panel frame-tick budget (`kPanelFrameTickUs`), not by the native-vs-library ratio alone: at ~198ms/call for a full-screen `frameCount=8` dispatch (pre-second-pass), a single dispatch already costs ~17x one frame tick's budget, so a full HQ waveform's few `frameCount=8` dispatches alone can dominate total wall-clock time regardless of how the ratio-to-library looks.
   - **Second optimization pass (loop-invariant hoisting + per-file `-O3` override), IN PROGRESS.** Two follow-ups once the ratio numbers above made clear the remaining gap was worth pursuing further:
     - `native_playback_kernel_plain`'s inner gather had two loop-invariant expressions recomputed from scratch on every iteration: `stride * (col - item->rectX0)` was recomputed 8x per group (it only depends on `col`, not on the row or group) and `mw*mw*word_idx + word_idx` was recomputed `num_groups*8` times per column (it's invariant across the *entire* call - depends only on `mw`/`word_idx`). Both hoisted to `col_base` (computed once per column, outside the group loop) and `lut_word_base` (computed once for the whole function call) respectively - a pure strength-reduction, provably identical arithmetic, no behavior change.
     - Discovered the project's `release` preset (the one actually used for real-hardware testing, per this file's own Build/Testing section) ships `CMAKE_BUILD_TYPE=MinSizeRel` (`-Os`, optimize for code size) - a reasonable default for the binary as a whole, but a bad fit for this one tight, compute-bound, per-pixel hot loop, where `-Os` intentionally skips optimizations like aggressive loop unrolling/scheduling that a numeric kernel benefits from. Added `set_source_files_properties(native_playback_kernel.cpp PROPERTIES COMPILE_OPTIONS "-O3")` in `tools/qsgepaper-preload/CMakeLists.txt`, scoped to just this one file (a later flag wins over the build type's `-Os`, confirmed via `ninja -t commands` showing `-Os ... -O3` in the final command line) - doesn't touch `CMAKE_BUILD_TYPE` or the rest of the binary's size.
     - **Confirmed correct on the emulator**, but only after a real scare: the first `swtcon-ab-test` native-vs-native determinism check after this change showed a 2-record `DISP` mismatch (`seq=32`/`33`, differing `sp3hash` only). Rather than assume the optimization was safe or broken, ran a controlled A/B: reverted just these two files to their pre-hoist/pre-`-O3` state (via the git index, which still held that exact prior state), rebuilt, and stress-tested **both** the old and new binaries with several independent sequential runs each (sequential is important - two concurrent runs on the emulator fight over the same pid-lock file and produce a misleading `swtcon_init failed`, not a real mismatch). Both binaries show the *identical* bimodal flake - the same two records, oscillating between the exact same two `sp3hash` value-pairs, at a similar rate, regardless of hoist/`-O3` - conclusively a **pre-existing race in the dispatch/render pipeline**, unrelated to Phase 9's playback-kernel work, most likely in whichever `ab_harness.cpp` scenario exercises un-synced overlapping submissions (the same style of intentionally-racy test as `qsgepaper-test`'s "burst of un-synced overlapping updates"). Left uninvestigated for now (out of scope for this pass) but worth a dedicated look later - see open item below.
     - **Emulator playback-kernel-bench after this pass:** native is now essentially at parity with `lib-plain` for small-to-medium rects (0.67x-0.99x) and only 1.2x-1.8x slower at half/full-screen (was 2.1x-4.1x after the first NEON-only pass); still 2.2x-5.7x slower than `lib-aligned` (the library's zero-per-call-setup fast path for phase-aligned dispatches, which this port doesn't yet special-case).
     - **Real-hardware confirmation of this pass (`real-dev-bench.txt`, updated again):** the hoist + `-O3` combination transferred to real silicon even better than the emulator numbers suggested - native is now **0.48x-1.74x** the library plain kernel's time (was 0.81x-3.42x after the NEON-only first pass, 3.3x-10.4x pre-NEON) and **1.43x-3.37x** the aligned kernel's (was 2.43x-6.58x, 5.2x-10.4x pre-NEON) - i.e. native is now often *faster* than `lib-plain` outright (tiny/text-row/menu all under 1.0x) and only middlingly slower at the largest sizes, a dramatic change from the original baseline.

Worth a dedicated investigation (likely in `ab_harness.cpp`'s un-synced-overlap scenario or the render/dispatch path it exercises) before trusting `swtcon-ab-test`'s determinism check as a hard invariant for unrelated future changes - right now it will intermittently report this one known-flaky pair as a false-positive "regression".
   - **Third pass: direct port of the real kernel's own vectorization strategy, from Ghidra disassembly (not decompile).** Real hardware still showed too-slow full-screen updates (visible as visual artifacts), so rather than continue tuning the from-scratch NEON transpose, went back to `libqsgepaper_3.23.0.54.so` via the Ghidra MCP tools and read `FUN_0004a140`'s case-8 handler (`frameCount=8`, confirmed the dominant real-world case - `get_function_by_address` shows Ghidra had already merged all the jump-table case bodies into one function, entry `0x4a140`, body `0x47c08`-`0x4a233`) directly as raw ARM/NEON disassembly (`disassemble_bytes`) rather than trusting the decompiler's pseudocode for such a heavily hand-scheduled function - the earlier decompile attempt produced an 86KB dump of near-unreadable `auVarN[16]`-soup for a much simpler dispatcher, a strong signal to read the assembly directly here too.
     - **What full byte-exact transliteration would have required, and why it was abandoned in favor of extracting the algorithm instead:** case 8 alone is ~366 instructions with heavy register reuse across a huge stack frame, a bulk per-column precompute pass (building several `num_groups`-sized scratch arrays via repeated calls to a helper at `0x1f960`, most likely a "fill sequential values" routine) whose exact memory layout was not fully pinned down before switching approach - continued manual tracing hit a real transcription error once (misread which value a reused register held across two different points in the function) confirming this is genuinely risky to hand-port byte-for-byte for code driving physical hardware. Presented this tradeoff to the user (full transliteration vs. extract-the-algorithm-and-reimplement vs. stop) - chose the middle path: extract the confirmed, high-value strategies and reimplement them cleanly, verified via the same probe/bench/ab-test infrastructure this codebase already uses rather than instruction-level fidelity to the compiler's own register allocation.
     - **The key algorithmic insight, successfully extracted and confirmed via the disassembly:** the real kernel vectorizes the *opposite axis* from the first NEON pass above. Instead of "load all 8 rows' LUT words into one vector, then for each of the 8 subphases extract+place+horizontally-reduce across rows" (the discarded first-pass strategy), it processes **one row at a time**, hardware-replicates that row's single LUT word into all 8 lanes of a vector via `VLD1.16 {dX[],dY[]}` (`vld1q_dup_u16` in intrinsics - confirmed by the `vld1.16 {d22[]-d23[]}, [r6]`-style disassembly, one per row), extracts *all 8 subphases* from that one replicated word in a single per-lane variable shift + mask (`vshl.u16`/`vand`, using a shift-constant vector loaded ONCE from a literal pool at function entry and reused unchanged for every row - confirmed via `vldr.64 d8/d9,[pc,#imm]` right after the setup code, matching `kExtractShiftAmounts = {0,-2,-4,...,-14}`), repositions that row's own 8 values into their shared bit range via a per-row **immediate** shift (`vshl.s16 qN,qN,#14/#12/.../#2` - one literal immediate per row, confirmed directly in the disassembly; row 7 uses no shift instruction at all, matching a `(7-7)*2=0` no-op), and accumulates via plain vector **ADD** rather than OR (safe because each row's field lands in a disjoint bit range - the 8 rows exactly tile the 16 bits with no overlap, so ADD and OR are equivalent with no possible carry across a field boundary). This eliminates the first pass's horizontal lane-reduce entirely (no `vext`/`vorr` fold chain at all) - the whole 8-subphase result falls out of the accumulator as one `vst1q_u16`, not a per-subphase scalar extraction.
     - **Reimplemented in `compute_shared_subphase_words`** (`native_playback_kernel.cpp`) using this exact strategy via intrinsics (`vld1q_dup_u16`, `vshlq_u16`, `vandq_u16`, `vshlq_n_u16` for the compile-time-immediate reposition shifts - manually unrolled per row, since `vshlq_n_u16` requires a true compile-time constant that a runtime loop variable wouldn't provide, matching the real kernel's own manual unrolling instead of a generic loop). Also applied one more strength reduction noticed in the same case-8 handler: the destination `byte_off(g)` formula is an arithmetic sequence in `g` with a constant 4-byte stride, so it's now a running accumulator per column (`byte_off += 4` per group) instead of a fresh multiply per group - the real kernel does something fancier (a bulk precompute across all groups via the scratch arrays above), but a running accumulator gets the same "no per-group multiply" benefit without needing extra scratch buffers.
     - **Confirmed correct on the emulator**: cross-compiled object disassembly shows exactly the intended instruction pattern (8x `vld1.16 {dX[]-dY[]}` / `vshl.u16` / `vand` / `vadd.i16` groups, 7x `vshl.s16 #imm` reposition shifts, **zero** `vext`/`vorr` anywhere - confirming the horizontal-reduce chain is genuinely gone, not just reordered). `swtcon-ab-test` native-vs-native determinism: only the same pre-existing `seq=32`/`33` race from the open item above, no new mismatches. Full `qsgepaper-test` interactive suite clean.
     - **Emulator `playback-kernel-bench` after this pass** (vs. the second pass's numbers): native is now essentially at or below parity with `lib-plain` across nearly the whole size range - 0.44x-1.30x (was 0.67x-1.8x) - and meaningfully closer to `lib-aligned` too - 2.19x-3.63x (was 2.19x-5.66x), with the biggest gains at medium/large sizes (half-screen: 0.99x vs. the second pass's 1.21x; full-screen fc=1: 1.30x vs. 1.75x). Real-hardware re-confirmation is still the next step for this pass specifically, same caveat as before - the emulator's software-emulated NEON timing doesn't necessarily scale the same way real Cortex-A7 silicon does.

# Building and Testing Steps

When testing on the local emulator (`RemEmu`), the physical `/dev/fb0` device does not exist. We use the `libioctl-dump.so` mockup library to intercept and handle `/dev/fb0` operations.

### 1. Compile
Build the project using `ninja` in the dev folder (no need for `nix` environment):
```bash
ninja -C build/dev
```

If you change a `CMakeLists.txt` (e.g. add a compile flag), ninja must reconfigure,
which needs the toolchain/pkg-config from the nix env. Reconfigure with:
```bash
PKG_CONFIG_PATH="" TOOLCHAIN_ROOT=/nix/store/1arv0dc51097f6g9kqhvlg74wrfwgybr-remarkable2-toolchain-5.0.58 cmake --preset dev
```

Note: `qsgepaper-test` is built with `_GLIBCXX_USE_CXX11_ABI=1` (the modern
default) so that our native `std::string`/`std::vector`/`std::list` layouts match
those in `libqsgepaper.so`. The library uses the **new** SSO string ABI: in
`qsgepaper_init` each `ModeEntry` name string is 0x18 (24) bytes, and
`FUN_0004535c` reads `ModeEntry::luts` at offset 0x18 — which only lines up with a
24-byte (new-ABI) `std::string`.

### 2. Upload to Emulator
Transfer both the test executable and the mocking library to the emulator:
```bash
scp build/dev/tools/qsgepaper-preload/qsgepaper-test build/dev/tools/ioctl-dump/libioctl-dump.so RemEmu:/home/root/
```

### 3. Run Test
Execute the test on the emulator using `LD_PRELOAD` to inject the framebuffer mock:
```bash
ssh RemEmu 'LD_PRELOAD=/home/root/libioctl-dump.so /home/root/qsgepaper-test'
```
Note that a successful run requires some input, see the `getchar()` calls.

### 4. A/B regression harness (`swtcon-ab-test`)

`swtcon-ab-test` (`ab_harness.cpp` + `ab_capture.cpp`) is the automated
differential test. It runs a fixed matrix of update sequences (overlap splits,
non-8-aligned rects, cross-batch overdraw - the cases that make an item's sp3
rebase offset nonzero) through the *real* pipeline and, when
`SWTCON_AB_CAPTURE=<path>` is set, records a sorted, pointer-normalized dump of:

- `DISP` - per surviving item after dispatch: narrowed rect, sp3 bounds, sp3
  content hash, and `stateDataPtr` as a u16 **offset** from `sp3.dataPtr`
  (`sdpoff`, the field the +0x44 bug got wrong);
- `PLAY` - each transient waveform frame, captured race-free on the display
  thread right after the playback kernel writes it (keyed by `seqId`/frame/slot);
- `STATE` - the settled state-buffer hash per step (the framebuffer ring is
  deliberately not hashed - the live worker thread races it).

The capture hooks live on the production path (`native_display.cpp`) and are
no-ops unless the env var is set, so this exercises exactly what ships. Run the
same input once native and once through the still-library dispatch
(`SWTCON_LIBDISPATCH=1`, the ground truth), then diff:

```bash
scp build/dev/tools/qsgepaper-preload/swtcon-ab-test RemEmu:/home/root/
ssh RemEmu 'cd /home/root && \
  SWTCON_AB_CAPTURE=/tmp/native.txt                     LD_PRELOAD=./libioctl-dump.so ./swtcon-ab-test && \
  SWTCON_AB_CAPTURE=/tmp/lib.txt SWTCON_LIBDISPATCH=1    LD_PRELOAD=./libioctl-dump.so ./swtcon-ab-test && \
  ./swtcon-ab-test --compare /tmp/native.txt /tmp/lib.txt'
```

`--compare` exits 0 on a full match, 1 on any divergence (printing the
localizing records), 2 on I/O error - so it drops straight into CI. Native runs
are deterministic, so two native captures also compare equal; that doubles as a
race check. Validated by reverting the +0x44 rebase: the harness fails and
points straight at the mismatched `sdpoff`/`PLAY` records.

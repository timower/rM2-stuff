# Swtcon Re-Implementation Plan & Status

Our goal is to sever the dependency on the black-box `libqsgepaper.so` library by fully reversing and re-implementing the Software Timing Controller (swtcon) logic natively in C++.

**The goal is full independence — no exceptions by default.** Every function
still called into the library by address (`resolve_ptr<...(*)...>(0x...)`) is
a dependency that needs to eventually go. Sizing something "large" just means
"port last, after everything smaller" — never "skip." As long as any
function is still called by address, the whole library stays `dlopen`'d and
mapped, so nothing is actually exempt.

**Update:** as of this pass, there are zero remaining by-address *function*
calls anywhere in the production pipeline (see Phase 5/6 and the playback-
kernel entry below) — the last one, `FUN_0004a234`, is gone. **Update 2:**
Phase 7 is also now done — every `resolve_ptr<T*>(addr)` *data* access into
the library's `.bss`/`.data` (the update-queue state, framebuffer/statebuffer
globals, mutexes, the dirty-gate array, a vtable pointer) has been replaced
with natively-owned storage (see the Phase 7 entry below). **Update 3: Phase
8 is done too** — by default this codebase never `dlopen`s `libqsgepaper.so`
at all anymore (confirmed via `/proc/<pid>/maps` on the emulator). The only
thing that still touches the library is `SWTCON_LIBIMPL=1`, a runtime env
toggle that switches every public swtcon_* entry point at once to the real
library (not a per-call-site splice), kept as a reference build for testing -
see the Phase 8 entry below. **Update 4:** dropped the `native_` prefix from
every function and source file in `tools/qsgepaper-preload/` (`native_init.*`
-> `init.*`, `native_update.*` -> `update.*`, `native_display.*` ->
`display.*`, `native_playback_kernel.cpp` -> `playback_kernel_intrinsics.cpp`,
and every `native_`-prefixed function declared in them). The prefix
distinguished the native reimplementation from library calls at individual
call sites; now that the native path is the only implementation left in the
production pipeline (`SWTCON_LIBIMPL` switches the *entire* binary at once,
not per-call-site - see Phase 8), there's nothing left for it to disambiguate
from. Two renamed functions collide by name with pre-existing symbols and
were given distinguishing names instead of a bare prefix-strip:
`playback_kernel_plain`/`playback_kernel_aligned` in
`playback_kernel_intrinsics.cpp` (the from-scratch NEON-intrinsics reference
port, not in the production dispatch path per the Phase 9 fifth-pass entry
below) became `playback_kernel_plain_intrinsics`/
`playback_kernel_aligned_intrinsics` to avoid colliding with the identically-
named `extern "C"` symbols defined in `playback_kernel.s`/
`playback_kernel_aligned.s` (the literal transliteration that *is* in the
production path).

See `swtcon_architecture.md` for a standing reference on *how the system
works* (data formats, control flow, algorithms, native and still-library
parts together, with confidence tags on anything not byte-verified). This
file tracks phase-by-phase porting *status* instead — what's done, what's
left, and what to do next.

- **`dispatch_processed_regions` — SOLVED, native, and WIRED IN (confirmed on the emulator).** What looked like a genuine cross-item rectangle-merge algorithm (an earlier framing) turned out, on empirical investigation via a dedicated tool (`tools/qsgepaper-preload/dispatch_processed_regions_probe.cpp` — calls the real library function directly with controlled synthetic `WorkItem` batches and reads back what actually happened, same technique as `render_kernel_addr_map.cpp`), to be **per-item-only bookkeeping with zero cross-item interaction** — 7 passing experiments including the definitive one (two independent items in one batch, dispatched together; the unrelated item's rect came back completely unaffected). Also nailed down `FUN_0004f8f0`/`FUN_0004e680`'s exact per-pixel packing formula: the packed transition value is `(oldState<<5)|newValue` and the "unchanged" sentinel is `0x0400`. See `swtcon_architecture.md` §6.2 step 4 / §6.3. The native port (`dispatch_processed_regions_native`/`commit_item` in `display.cpp`) is wired in at the real call site. **The "integration hazard" that previously kept it by-address — a deterministic SIGSEGV in the still-library `FUN_0004a234` on the first HQ update — was a stale `WorkItem.stateDataPtr` (+0x44), not `FUN_0004a234` itself.** The real `dispatch_processed_regions` caches `sp3.ptr->dataPtr` into `item+0x44` right after allocating `sp3`, and both playback kernels (`FUN_0004a140`/`FUN_0004a234`) read their per-pixel state through that cached pointer, not via `sp3.ptr->dataPtr`; `commit_item` now sets it. That's exactly why the earlier elimination log (not downstream state, not `sp3` content, not timing, not global init) came back all-negative — none of those touched +0x44. **Confirmed on the emulator** with the native path live: clean `EXIT=0` across HQ/medium/clearing plus all five overlap tests, continuous `FBIOPAN`, clean shutdown. **Confirmed on hardware too**, after one follow-up fix: +0x44 is not the sp3 buffer *base* — it's that base **rebased to the item's post-narrowing rect origin** (`sp3.dataPtr + stride*(rectX0-sp3.x0) + (rectY0-sp3.y0)`, the same rebasing as `gap` vs `regionRows`). The incremental commit narrows `item.rect` inward from the 8-aligned seed the sp3 buffer was sized for, and the playback kernels index +0x44 with narrowed-rect-relative coords. Seeding it to the base (offset 0) is correct only for the force path and unsplit items; for any narrowed/split item it read state one column + 8 rows off → **edge artifacts** (white seams where an update overdrew a previous one), visible only on real e-ink since the digital state/framebuffer settle identically. Found via a native-vs-library A/B harness (`SWTCON_LIBDISPATCH` env toggle, still in `display_thread_func`) that diffs the *transient* waveform frames — the library's +0x44 came back as `sp3.dataPtr + 0x670` on a narrowed item, exactly `stride*(804-803)+(1072-1064)`. `commit_item` now rebases it after narrowing.

- **`FUN_0004a140` ("plain" playback kernel) — SOLVED, native, and WIRED IN (confirmed on the emulator).** Reversed via `tools/qsgepaper-preload/playback_kernel_probe.cpp`, the same "dlopen the real library, call the real function directly with a controlled synthetic `WorkItem`, read back what happened" technique as `render_kernel_addr_map.cpp`/`dispatch_processed_regions_probe.cpp`. Every buffer the probe hands the kernel (state buffer, LUT data, the `frameSlots[8]` pointer array itself, even the `WorkItem`'s own containing node) is backed by an `mmap` `PROT_NONE` guard page on both sides — a first pass with plain `malloc`'d buffers found the kernel call "returns without crashing" but silently corrupts memory, discovered only much later at an unrelated `free()`; guard pages turn that into an immediate, localizing `SIGSEGV`. (The actual first corruption culprit turned out to be a bug in the probe itself, not the kernel: `LUTEntry`'s destructor unconditionally `free()`s `.data`, and `TestItem` embedded a `LUTEntry` by value, so it fired on every guard-paged LUT buffer at scope exit — nulling `.data` before that fixed it. Worth remembering next time a "clean return, corruption discovered later" pattern shows up: check for an implicit destructor on a raw pointer field before suspecting the library call.) When black-box probing alone stalled (zero output from a plausible-looking call), reading `FUN_0004a140`'s Ghidra decompile directly (via the `mcp__ghidra__decompile_function` MCP tool, `libqsgepaper_3.23.0.54.so`) resolved it immediately rather than more guessing. Fully confirmed and ported (`playback_kernel_plain_intrinsics` in `display.cpp`):
  - The LUT-index formula matches the already-native `read_lut_packed_pixel` exactly: the raw `stateDataPtr` (+0x44) u16 per pixel is used directly as `mw*row+col` (a flat multiply-add, *not* a `>>5`/`&0x1f` split — only numerically identical to the `(oldState<<5)|newState` packing confirmed elsewhere in this codebase because `mode_width==32` in that case).
  - The destination address formula: `frameSlots[k] + ((col + 3)*0x104 + (rectY0>>3) + group + 0x1a) * 4` (`col` absolute, `group` the 0-based 8-row-group index within the rect, `k` the output-frame index) — byte-verified against five targeted probe experiments (single group, multi-group at `base+group*4`, and multi-column chunking).
  - Y is block-quantized by 8 (`((rectY1-rectY0)+1)>>3` gates the whole write loop — a literal 1×1 test rect silently no-ops here, which is why the probe's first few runs produced zero output with no error); X is not block-quantized.
  - Drive values are 2-bit; within one 8-row group, row `r` (0-based from the group's start) OR-accumulates into bit position `(7-r)*2` of a 16-bit word — row 0 at the *top*, row 7 at the *bottom* (confirmed via 8 isolated single-row probe experiments), matching this codebase's established 180°-rotation convention rather than a naive lane order.
  - `frameCount` (1–8) does **not** mean N independent LUT lookups: the kernel computes an 8-entry shared buffer once per column/row-group (one entry per possible sub-phase 0–7 packed into the current LUT word) and `frameSlots[k]` just reads out shared-buffer entry `(phase&7)+k` — confirmed both by decompiling case 2 and by a probe experiment planting two different values at adjacent sub-phases of the same LUT word and observing them land in `frameSlots[0]`/`frameSlots[1]` respectively. This is exactly why `advance_work_item_frames` always picks `frameCount` so `phase&7+frameCount` never crosses an 8-sub-phase LUT-word boundary — the native port needs no case-by-case logic at all, just one parametrized loop.
  - `FUN_0004a140`'s prologue jump-tables on `frameCount` 0–8; case 0 falls through to a *second*, Ghidra-unrecoverable nested jump table (`Could not recover jumptable at 0x47be8`) — irrelevant here since `advance_work_item_frames` never calls the plain-kernel path with `frameCount==0` (guarded by its own early-return).
  - The function calls no allocation/free, touches no global (`DAT_*`) addresses, spawns no threads, and never writes to `*item` — every `item` field it touches (`0xc`/`0x10`/`0x14`/`0x18`/`0x28`/`0x2c`/`0x3c`/`0x44`) is read-only, and mode_width/bit_depth aside, the 2-bit/8-row packing constants are hardcoded immediates in the real kernel too (matches `load_waveform` always producing `bit_depth=2` LUTs).
  - **Confirmed on the emulator** via the full `swtcon-ab-test` A/B pipeline (not just the isolated probe): `KERN` log coverage shows the real test matrix exercises the plain kernel exclusively at `frameCount=8`; a native-vs-library `--compare` run matched byte-for-byte everywhere except `seq=26-29`, which is the pre-existing documented real-time-jitter window (case 8/9's `usleep`-based submissions) — confirmed noise, not a regression, since a native-vs-native rerun shows the identical mismatch pattern with the library entirely out of the loop.
- **`FUN_0004a234` (playback kernel; formerly called "overlap-aware" here - corrected to "aligned", see below) — SOLVED, native, and WIRED IN (confirmed on the emulator).** Turned out **not to be a distinct algorithm at all.** Rather than reversing it independently, a decisive test (`playback_kernel_probe.cpp` Experiment 7) calls both `FUN_0004a140` and the real `FUN_0004a234` on an *identical* synthetic `WorkItem`/state/LUT (a rich, pseudo-random, non-uniform fill spanning 4 columns × 16 rows, so a coincidental match is implausible) for every `frameCount` 1–8 — **including the three cases (1, 2, 3) that `FUN_0004a234` itself tail-calls out to separate, still fully unreversed delegates** (`FUN_0004a3f8`/`FUN_0004a9e0`/`FUN_0004b098`) **for** — and diffs every byte of the output: all eight cases came back byte-for-byte identical. A Ghidra decompile of case 8 (94/117 real overlap-kernel calls in one `ab-test` run, vs. 23 for case 5 and 0 for every other case — checked via the `KERN` log before investing in a decompile) independently corroborates this: it touches the *exact same* `WorkItem` fields as `FUN_0004a140` (`0xc`/`0x10`/`0x14`/`0x18`/`0x28`/`0x2c`/`0x3c`/`0x44`), the same LUT-index formula, the same destination address formula, and the same row→bit packing order — no new field, no global, no `intList` access, no allocation, no threads. The only difference is NEON unrolling strategy: cases 4–8 extract all 8 sub-phases from one lane-shifted vector at once (valid only because the selection rule guarantees `phase&7==0` whenever this path is taken, so there's no `(phase&7)+k` offset to compute, unlike `FUN_0004a140`'s general case). **Naming correction (this pass): `FUN_0004a234` and its dispatch wrapper were previously called "overlap-aware"/`native_dispatch_overlap_kernel` — backwards, since (per `advance_work_item_frames`'s selection rule, `swtcon_architecture.md` §6.4) this path fires exactly when there is *no* active overlap dependency left, gated only on `phase&7==0`. Renamed to "aligned"/`dispatch_aligned_kernel` throughout the code, the `KERN` A/B-capture log tag, and this doc.** **Net result: `playback_kernel_plain_intrinsics` now backs *both* `dispatch_plain_kernel` and `dispatch_aligned_kernel`** (`display.cpp`) — one native function, zero remaining by-address playback-kernel calls, and the three delegates never need reversing at all. **Confirmed on the emulator**: the full `swtcon-ab-test` A/B pipeline's `STATE` records (the settled, final pixel-level output per test step) match the library **perfectly, zero mismatches, across all 9 test cases** — the only remaining `--compare` divergences are transient `PLAY` per-frame-capture timing jitter (inherently real-time-dependent, the same documented class of noise as `seq=26-29`'s case 8/9 window, now also touching `seq=10` purely because native code runs at different wall-clock speed than the by-address call did, shifting which real-time frame tick a capture lands on — confirmed non-causal by reproducing the identical `seq=10` mismatch in a native-vs-native rerun with the library entirely out of the loop) and the pre-existing, already-documented `seq=28/29` `DISP` noise. `qsgepaper-test`'s full interactive suite (including the two playback-coverage scenarios) also runs clean, `EXIT=0`, on the emulator.
  - **Follow-up ("there must be a reason they're separate functions"):** decompiling `FUN_0004a3f8` (case 1's delegate) directly answers this — the code really is meaningfully different, not a trivial duplicate. It does alignment-based column-chunking (`-(((uint)ptr & 0x3f) >> 4) & 3`-style leading/trailing-remainder splitting) and an 8×4 transpose/prefetch bulk loop, structurally unlike `FUN_0004a140`'s simple one-column-at-a-time loop — genuine hand-tuned NEON engineering, most likely per-`(frameCount, phase-alignment)` performance specialization (`FUN_0004a140` is the fully general case, needing the `(phase&7)+k` slice for arbitrary alignment; `FUN_0004a234`'s cases 4-8 and the three delegates are all fast paths only valid at `phase&7==0`, some further specialized for wide-column bulk throughput). Critically, it still touches only the *exact same* `WorkItem` fields as everything else here — no `intList`, no new global, no allocation — so "why a separate function" has an engineering answer (performance), not a semantic one (no code path here has any way to observe or react to *another* item's overlap-dependency state; that's entirely the caller's `advance_work_item_frames` selection-rule's job, see `swtcon_architecture.md` §6.4). Re-ran the identical-input diff specifically designed to stress the parts that differ - a 128-column rect (wide enough to exercise the bulk transpose path, not just the tail/remainder handling a narrow rect would trivially hit either way) and explicit `chunkCount=2` splitting (exercising `FUN_0004a3f8`'s own independently-computed chunk boundary, not just `FUN_0004a140`/`FUN_0004a234`'s shared one) - still byte-for-byte identical across every case. Xrefs confirm neither kernel is called from anywhere but its own wrapper (`FUN_0003f294`/`FUN_0003f1f0`), so there's no other call site hinting at a different intended use either.

- **Phase 7 — Global storage independence: COMPLETE (confirmed on the emulator).** Every remaining `resolve_ptr<T*>(addr)` *data* access into the library's `.bss` is gone - the four structs (`UpdateQueueGlobals`, `FrameCursorGlobals`, `StatebufferGlobals`, `FramebufferGlobals`), the four standalone scalars (pid fd, cached temperature, temperature mutex, seq counter), the backBuffer dirty-gate array, and the RegionRows shared_ptr vtable are all natively-owned storage now (`qsgepaper_globals.h`'s accessors are function-local `static` instances instead of `resolve_ptr<T*>(fixed_addr)`; `update.cpp`'s `kNativeRegionRowsVtable` mirrors the `dispose`=array-delete/`destroy`=delete convention `make_empty_lut`'s `kNativeLutVtable` and `display.cpp`'s `kNativeSp3Vtable` already used). The three previously-implicit pieces got added, not just relocated: the three `ListHead` sentinels (`listProcessedUpdates`/`listIncomingUpdates`/`accumList`) are now explicitly self-referenced at the top of `swtcon_init`; the waveform vector (`g_nativeWaveformStruct` in `swtcon.cpp`, no longer "deliberately leaked") is walked and freed in `swtcon_shutdown`; the temperature mutex gets an explicit `pthread_mutex_init` alongside the others. As a genuine drive-by fix (not scope creep - it's the same pid-fd global this phase was already touching): `unlock_pid_file` was reading the *library's* still-zero pid-fd slot instead of `create_pid_file`'s own `g_nPidFdNative`, a latent dead-code bug now corrected.
  - **Two real bugs surfaced during validation, both worth remembering.** First, `stale_row_cleanup`'s documented "backward `i%16` reach" quirk (§ next steps below) used to land safely in the library's own huge `.bss` region; a bare native array has no such margin, so the first swtcon-ab-test run after the refactor **segfaulted immediately at startup**. Fixed by padding `backbuffer_dirty_gate()` with `kDirtyGateBucketCount` extra always-zero buckets before the real array and returning a pointer into the middle - same observable behavior (the padding is provably never legitimately written), just safe to reach. Second, and much more interesting: fixing the first bug uncovered a **pre-existing, silent heap-buffer-overflow read in `playback_kernel_plain_intrinsics`** (`display.cpp`, dates to Phase 5) that had nothing to do with Phase 7's own diff - it read `state[sp3->stride*(col-sp3->x0)+(row-sp3->y0)]`, double-applying the sp3-rebase offset on top of a `stateDataPtr` that's *already* rebased to the item's own rect origin (see `commit_item`'s +0x44 comment), overrunning the sp3 buffer for any narrowed item by up to a few hundred bytes. It had been silently reading adjacent-but-mapped heap memory for every phase up through Phase 6 without ever crashing or showing up in an A/B mismatch; Phase 7's different static/heap layout was enough to occasionally push the same over-read into an unmapped page, turning silent corruption into a hard, semi-reproducible `SIGSEGV`. Root-caused in minutes rather than hours via a throwaway AddressSanitizer build (`cmake --preset dev -B build/asan -DCMAKE_CXX_FLAGS="-fsanitize=address -g -O0 -fno-omit-frame-pointer" -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address"`, then `LD_PRELOAD=./libasan.so.8:./libioctl-dump.so` with `libasan.so.8.0.0` copied over from the toolchain sysroot) - it caught the exact faulting read, the exact allocation site, and the exact overrun distance on the very first narrowed item, no manual bisection needed. Worth remembering for next time a native port "works" on every A/B run but only because the overrun is silently landing on other live heap data: **when a bug is timing/layout-sensitive and a plain SIGSEGV handler's backtrace is too shallow to trust (ARM's `backtrace()` frequently can't unwind through a signal frame - a `SA_SIGINFO` handler reading `ucontext_t.uc_mcontext.arm_pc` directly is more reliable), reach for ASan before hand-bisecting.** Fixed by indexing `state[]` relative to the item's own rect origin (`stride*(col-item->rectX0)+(row-item->rectY0)`) instead of sp3's - algebraically the same absolute buffer element, but without the double offset; the item's rect is always a subset of sp3's outward-8-aligned rect, so this is provably always in-bounds. Confirmed clean under the ASan build afterward (aside from one unrelated, harmless, pre-existing `malloc`/`operator delete` mismatch in `free_statebuffer`'s gamma-table free, suppressed via `alloc_dealloc_mismatch=0` - glibc's `free()` and libstdc++'s default `operator delete` are the same function under the hood, so this is a strictness-only ASan complaint, not a real bug).
  - **Validation caveat:** the existing `SWTCON_LIBDISPATCH=1` A/B path (real library's `dispatch_processed_regions` called by address) is now **structurally non-functional**, not a new regression to chase - it depends on the native side and the library sharing the same backing globals, which is exactly what this phase removes. Calling it now reliably `SIGSEGV`s on the real function reading its own (now permanently stale) `.bss`. Validated instead the way this codebase already validates native determinism: two independent post-fix `swtcon-ab-test` runs captured byte-for-byte identical (`--compare` exit 0, 3994/3994 records), plus a full `qsgepaper-test` interactive run (`EXIT=0`). Byte-diffing against a pre-Phase-7 capture turned out not to be meaningful either - real-time backlog ("generator thread has fallen behind...") volume varies a lot run-to-run regardless of phase, so record *counts* differ; determinism (this run vs. itself) is the correct invariant here, not sameness against an unrelated run's capture.
- **Phase 8 — Remove `dlopen` from the production path: COMPLETE (confirmed on the emulator).** `SWTCON_LIBDISPATCH` (the old per-call-site A/B splice, already noted above as structurally non-functional post-Phase-7) is gone entirely, replaced by `SWTCON_LIBIMPL` (`swtcon_libimpl.h`/`swtcon_lib_impl_enabled()`): a single runtime env toggle that switches every public swtcon_* entry point (`init`/`lock`/`update`/`unlock_post`/`wait`/`shutdown`) at once between the native implementation and the real library's own by-address exports, instead of splicing library calls into individual native call sites. This sidesteps Phase 7's "native and library don't share globals" problem entirely - each mode is wholly self-contained, so there's no shared-state assumption to break. `load_lib()` (`swtcon.cpp`) now only runs inside `swtcon_lib_impl_enabled()` branches; by default nothing `dlopen`s `libqsgepaper.so` at all. `swtcon_shutdown`'s library-mode branch calls the library's own `actualShutdown` (`0x3b6b4`) by address - like every other public entry point in this mode - rather than re-running the native shutdown reimplementation against the library's own `UpdateQueueGlobals` via `resolve_ptr` (an earlier, inconsistent version of this branch); Ghidra decompile of `0x3b6b4` confirms it's exactly the drain-queues/signal+join-both-threads/save-statebuffer/blank+free-framebuffer-statebuffer-LUT/unlock-pid-file sequence the native branch below already mirrors, so nothing native was ever allocated in this mode either. Confirmed via `/proc/<pid>/maps` on the emulator: no `libqsgepaper.so` mapping with `SWTCON_LIBIMPL` unset, present with it set to `1`; both modes run the full interactive test suite clean (`EXIT=0`), with the library's own `puts()` shutdown log lines now visible in library mode confirming the real function is running.

(Also found two harmless micro-optimizations not worth porting: row 7, whose reposition shift is 0, reuses the accumulator register directly instead of a separate zero-init+add; the shift-14 lane skips its `vand` mask entirely because a left-shift-by-14 on a 16-bit lane already discards everything above the bottom 2 bits, making the mask redundant for that one lane only. Both are compiler-level peephole tricks worth at most 1-2 instructions - not worth the complexity/risk of replicating by hand.)
     - **Ported the one safe, high-value piece:** the gather loop in `playback_kernel_plain_intrinsics` now does `vld1q_u16(&state[idx0])` once per group (the 8 rows are contiguous in `state`, confirmed by construction - `idx` increases by exactly 1 per row) instead of 8 separate scalar reads, then extracts each lane with `vgetq_lane_u16` for the (necessarily still scalar - no gather instruction on this target) LUT-word lookup. Scalar `#else` fallback unchanged.
     - **A real scare during verification, resolved by tracing causality rather than more sampling:** the standard determinism stress test surfaced a **third**, never-before-seen `sp3hash` value for the known-flaky `seq=32`/`33` `DISP` record (previously only ever `7d903c73`/`2d9f4db7` or `518436e3`/`7a7e7b47` across many samples - see the open item above). Rather than wave it off as "more of the same" or panic and revert, traced *causality*: `ab_capture_dispatch` (the `DISP` capture) is called from `display.cpp`'s incoming-batch-dispatch path (`dispatch_processed_regions_native` + `ab_capture_dispatch`, ~line 990) - strictly at commit time, on the display thread, for every batch as it's dispatched. `playback_kernel_plain_intrinsics` (this pass's only change) is called later, from a completely different code path (`advance_work_item_frames`, driven by the worker thread's per-tick pacing), and only *reads* `stateDataPtr`/`sp3` - it never writes back into anything `ab_capture_dispatch` hashes. There is therefore no code path by which a change to the playback kernel's read logic can *causally* alter a `DISP` record's `sp3hash` - only *indirectly*, by shifting overall thread timing/pacing enough to change which racy interleaving of concurrent test-harness submissions gets captured at that sequence number (the same class of benign, timing-driven noise already documented for `PLAY` records at `seq=10`/`26-29`). Confirmed empirically too: re-ran 8 sequential captures on both this pass's binary (3 distinct values: `ec2255bf`x1, `518436e3`x5, `7d903c73`x2) and the previous, unmodified committed binary (2 distinct values in this particular 8-run sample: `518436e3`x6, `7d903c73`x2) - consistent with the same underlying race simply having a wider outcome space than the 2 values sampled so far, not a new bug. Updated the open item below to record the wider observed set.
     - **Confirmed correct otherwise:** full `qsgepaper-test` interactive suite clean (HQ/medium/clearing + overlap tests, continuous `FBIOPAN`, clean shutdown) on this pass's binary.
     - **Emulator `playback-kernel-bench` after this pass:** native is now **0.47x-1.03x** of `lib-plain` (was 0.44x-1.30x) - essentially full parity across the whole size range, sometimes faster - and **1.75x-3.46x** of `lib-aligned` (was 2.19x-3.63x). Real-hardware re-confirmation is still the next step, same caveat as every prior pass.
   - **Fifth pass: real-hardware artifacts traced to the kernel specifically, then fixed by abandoning intrinsics for a literal disassembly transliteration.** Despite the fourth pass's clean emulator numbers, real hardware still showed a ~710-720ms first HQ full-screen update with visible visual artifacts on gray content (worst on the single-edge-overlap test). Root-caused the *kernel choice itself* as the cause - not a suspected pipeline race - via a decisive experiment: swapping `dispatch_plain_kernel`/`dispatch_aligned_kernel` to call the real by-address `FUN_0004a140` for *both* wrappers (bypassing `playback_kernel_plain_intrinsics` entirely) made the artifacts disappear and brought timing back to ~250ms, on otherwise-unchanged dispatch/pacing/race-prone code - ruling out a pipeline race (the user's own objection: "that still doesn't explain why using the library's kernel fixes it, the dispatch logic would have the same race condition"). Two follow-up hypotheses were then tested and **refuted**: (1) panel pan cadence being software-paced (a new `pan_timing.h`/`.cpp` wall-clock logger showed `FBIOPAN_DISPLAY` blocks a near-constant ~11.87ms regardless of kernel choice - hardware/vsync-paced, not software-paced); (2) the intrinsics kernel suffering disproportionate 2-thread self-contention (extended `playback_kernel_bench.cpp` to run genuine 2-thread concurrent dispatch - it showed near-perfect ~0.51x scaling and an unchanged native-vs-library ratio going from 1 to 2 threads, contradicting the much worse ratio seen in real-pipeline `KERNDISPATCH` logs for nominally the same rect sizes - left unreconciled, since a different fix landed first). Also confirmed via a dedicated `playback_kernel_probe.cpp` Experiment 8 (non-8-aligned origin *and* non-8-aligned height, every `frame_count`, both chunk splits) that `playback_kernel_plain_intrinsics`'s output is byte-for-byte identical to the real library kernel even at those boundary conditions - so the divergence was never a static correctness bug this codebase's black-box verification could catch.
     - **The actual fix: `tools/qsgepaper-preload/playback_kernel.s` / `playback_kernel_aligned.s`**, a direct, essentially line-for-line transliteration of `FUN_0004a140`'s and `FUN_0004a234`'s full Ghidra disassembly (every jump-table case, including `FUN_0004a234`'s previously-never-ported delegates at `0x4a280`/`0x3a3f8`/`0x3a9e0`/`0x3b098`/`0x3a3a8`->`0x3b7f0`/`0x3bfb8`/`0x3c860`/`0x3d1c0`) into hand-assembled ARM/NEON `.s` files, compiled directly (`project(qsgepaper-preload CXX ASM)`) and linked in as `extern "C" void playback_kernel_plain(...)`/`playback_kernel_aligned(...)`, replacing the `playback_kernel_plain_intrinsics` intrinsics port at both dispatch call sites in `display.cpp`. **This reverses the third pass's explicit decision (above) to avoid full byte-exact transliteration** - that earlier tradeoff call turned out to be wrong for this specific case: the intrinsics port was algorithmically sound enough to pass every black-box check this codebase has (isolated probe, full-pipeline A/B capture-and-diff, benchmark parity) yet still differed from the real kernel in some way real e-ink hardware is sensitive to and none of those checks are. **The root cause of that behavioral difference was never identified** - worth remembering next time an intrinsics/reimplementation port "verifies clean" on every available check: on this hardware target, that is evidently not sufficient proof of equivalence, and a literal transliteration is the fallback of last resort, not just a discarded option.
     - **A real build-breakage bug found and fixed while verifying this pass**: `swtcon-ab-test` and `playback-kernel-bench`'s `CMakeLists.txt` entries link `display.cpp` (which now calls the two new `extern "C"` symbols) but had not been updated to compile `playback_kernel.s`/`playback_kernel_aligned.s`, so both failed to link (`undefined reference to playback_kernel_plain/playback_kernel_aligned`) the moment the fix landed - only `qsgepaper-test`'s entry had been updated. Fixed by adding both `.s` files to those two targets' `add_executable()` too.
     - **Confirmed on the emulator** after that fix: all four affected targets (`qsgepaper-test`, `swtcon-ab-test`, `playback-kernel-bench`, `playback-kernel-probe`) build clean; `swtcon-ab-test`'s standard determinism check (two independent native runs, `--compare`) matches **3994/3994 records** with zero divergence. Real-hardware re-confirmation of this specific fix (does it still run clean under the full interactive suite, not just fix the originally-reported artifacts) is still pending, same as every prior Phase 9 pass.
     - **`playback_kernel_plain_intrinsics` (the intrinsics NEON port) is no longer in the production dispatch path** but is kept around and still compiled/linked - `playback_kernel_bench.cpp` still benchmarks it for comparison purposes, and it remains a from-scratch reference implementation of the same algorithm the fourth pass's analysis (case-8 gather/replicate/extract/reposition/accumulate strategy) was based on.

# Building and Testing Steps

When testing on the local emulator (`RemEmu`), the physical `/dev/fb0` device does not exist. We use the `libioctl-dump.so` mockup library to intercept and handle `/dev/fb0` operations.

### 1. Compile
Build the project using `ninja` in the dev folder (no need for `nix` environment):
```bash
ninja -C build/dev
```

If you change a `CMakeLists.txt` (e.g. add a compile flag), ninja must reconfigure,
which needs the toolchain/pkg-config from the nix env. Reconfigure with:
```bash
PKG_CONFIG_PATH="" TOOLCHAIN_ROOT=/nix/store/1arv0dc51097f6g9kqhvlg74wrfwgybr-remarkable2-toolchain-5.0.58 cmake --preset dev
```

Note: `qsgepaper-test` is built with `_GLIBCXX_USE_CXX11_ABI=1` (the modern
default) so that our native `std::string`/`std::vector`/`std::list` layouts match
those in `libqsgepaper.so`. The library uses the **new** SSO string ABI: in
`qsgepaper_init` each `ModeEntry` name string is 0x18 (24) bytes, and
`FUN_0004535c` reads `ModeEntry::luts` at offset 0x18 — which only lines up with a
24-byte (new-ABI) `std::string`.

### 2. Upload to Emulator
Transfer both the test executable and the mocking library to the emulator:
```bash
scp build/dev/tools/qsgepaper-preload/qsgepaper-test build/dev/tools/ioctl-dump/libioctl-dump.so RemEmu:/home/root/
```

### 3. Run Test
Execute the test on the emulator using `LD_PRELOAD` to inject the framebuffer mock:
```bash
ssh RemEmu 'LD_PRELOAD=/home/root/libioctl-dump.so /home/root/qsgepaper-test'
```
Note that a successful run requires some input, see the `getchar()` calls.

### 4. A/B comparison (`SWTCON_LIBIMPL` + pan-capture)

The old internal differential harness (`swtcon-ab-test`/`ab_harness.cpp`/
`ab_capture.cpp`, which instrumented `display.cpp` directly and relied
on `SWTCON_LIBDISPATCH` splicing individual by-address library calls into the
native pipeline) is gone - it depended on native and library code sharing
process globals, which Phase 7 removed. It found real bugs in its time (the
+0x44 rebase bug, the `seq=32`/`33` race) and is worth remembering as a
technique if a similar internal-state differential ever becomes useful again,
but it no longer exists in the tree.

In its place: `SWTCON_LIBIMPL=1` (see Phase 8 above) runs `qsgepaper-test`
entirely through the real library instead of the native path - no shared
state with a native run at all, since each run is wholly one or the other.
Compare two runs externally, at the ioctl level, via
`libioctl-dump.so`'s `SWTCON_PAN_CAPTURE=<path>` (hashes the framebuffer
content on every `FBIOPAN_DISPLAY` call, deduped against the immediately
preceding pan - ring slot index doesn't matter, only the sequence of
actually-displayed content) and `pan-capture-compare`. The easiest way to run
this is `tools/qsgepaper-preload/ab_compare.sh <ssh-target> [test-case]`,
which handles the upload/run/compare sequence below automatically:

```bash
scp build/dev/tools/qsgepaper-preload/qsgepaper-test \
    build/dev/tools/ioctl-dump/libioctl-dump.so \
    build/dev/tools/ioctl-dump/pan-capture-compare RemEmu:/home/root/
ssh RemEmu 'cd /home/root && \
  SWTCON_PAN_CAPTURE=/tmp/native.txt                LD_PRELOAD=./libioctl-dump.so ./qsgepaper-test && \
  SWTCON_LIBIMPL=1 SWTCON_PAN_CAPTURE=/tmp/lib.txt   LD_PRELOAD=./libioctl-dump.so ./qsgepaper-test && \
  ./pan-capture-compare /tmp/native.txt /tmp/lib.txt'
```

**Important caveat, confirmed empirically:** what's panned is per-phase e-ink
drive signal, not settled pixel state, and both real-time frame pacing and
legitimate cross-slot content repetition (e.g. during blank/priming) make a
positional/count comparison meaningless *across a whole-suite run* - a raw
native-vs-library diff of the whole ten-test suite showed 4x different pan
counts purely from wall-clock speed differences. That's only true at
whole-suite granularity, though: `main.cpp`'s test-case-number argument lets
each of the ten tests be run and captured in isolation, and *within one
isolated test case* the two runs do produce the same ordered sequence of
displayed content (confirmed: nine of ten test cases match position-for-
position). So `pan-capture-compare` does an **ordered** (positional) hash
compare - hash at position i in one capture vs. position i in the other -
rather than the set-of-distinct-hashes compare it used to do; a raw
whole-suite capture is no longer a supported input; only isolate-and-compare
per test case as `ab_compare.sh` does.

`ab_compare.sh` runs every test case except case 8 ("burst of un-synced
overlapping updates") by default - it deliberately submits updates with no
`swtcon_wait()` between them, racing the worker thread by design, so it is
known-flaky under any A/B comparison and not a real regression signal (21
native-only + 12 library-only hashes out of 45/36 total, entirely explained
by real-time interleaving noise - see the Phase 8 entry above). Pass "8"
explicitly to `ab_compare.sh` to check it anyway. Every other test case is
expected to match exactly; a mismatch there is a real signal worth
investigating (a natural next step for `playback_kernel_plain_intrinsics`'s
still-unexplained real-hardware artifact from Phase 9's fifth pass, above).
